---
name: Stale composite-project dist blocks tsc after schema/type changes
description: tsc -p (non --build mode) on api-server can report phantom "no exported member" / "property does not exist" errors from stale referenced-project .d.ts files.
---

`artifacts/api-server/tsconfig.json` uses TS project `references` (e.g. to
`lib/db`, `lib/permission-keys`) but is typechecked with plain
`tsc --noEmit -p .`, NOT `tsc --build`. Referenced composite projects
(`composite: true`, `emitDeclarationOnly: true`) are consumed via their
committed `dist/*.d.ts` files, which are only regenerated by an explicit
build — not by editing `src/`.

Symptom: after a schema/type change lands in `lib/db` (or any other
referenced lib package) but before its `dist/` is rebuilt, `tsc --noEmit -p
artifacts/api-server` reports errors like "Module has no exported member
X" or "Property X does not exist" for symbols that clearly exist in the
package's `src/`. This can look like a real regression across many
unrelated files.

**Why:** the referenced project's stale `dist/*.d.ts` (checked into the
repo, not gitignored in this workspace) is what TS actually resolves for
`@workspace/<pkg>` imports outside `--build` mode; also make sure
`pnpm install` has linked any newly-added workspace package into
`node_modules/@workspace/*` symlinks (a package added to package.json but
never installed produces a real "Cannot find module" instead).

**How to apply:** when `tsc --noEmit` on api-server (or another consumer)
shows errors that don't match the current source of a `@workspace/*` lib
you or someone else just changed, run
`pnpm --filter @workspace/<pkg> exec tsc --build --force` for that lib
first, then re-run the consumer's typecheck before concluding there's a
real bug.
